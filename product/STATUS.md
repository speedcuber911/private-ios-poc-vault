## First real trial run — what it broke, 2026-08-13

The first end-to-end use of a trial sandbox by its owner. Everything below was
found by using the product, not by review, and every one of them affected
**every** trial user rather than just this account.

| Fault as the user saw it | Root cause | Fix |
|---|---|---|
| Notifications never arrived | `APNS_HOST` was `api.sandbox.push.apple.com` while the installed build was TestFlight (production). Apple answers a wrong-environment token with `400 BadDeviceToken`, and the classifier treated that as "app uninstalled" and **deleted the token**. Both device rows registered at 14:13 were wiped within four minutes; the fanout ended at `devices=0` | `3be4641` — only `410` may delete a token now. `BadDeviceToken`/`DeviceTokenNotForTopic` became `BAD_TOKEN`: counted, alerted with the host named, never deleted |
| One global APNs host cannot serve one account | Flipping the host to production then refused the other 27 tokens instead — `badToken=27` on every push. A token is only valid against the environment of the build that minted it | `d2fa957` — `devices.apns_environment` (non-destructive migration); host chosen per device at send time; `NULL` falls back to the configured default so nothing pre-existing moves. iOS reports it from the embedded provisioning profile's `aps-environment`, **not** `#if DEBUG` (a Release build installed from Xcode still gets a development token and would lie) |
| Fanout log reported more deliveries than devices | The summary diffed the process-wide `stats` across its `await`, and ingest does not await the fanout — so overlapping fanouts each counted the other's outcomes. A 27-device fanout logged `delivered=43` | `3be4641` — counted per fanout as outcomes happen. The log is now internally consistent (`devices=29 badToken=27 delivered=2`) |
| App stranded after a TestFlight reinstall | The PKCS#12 identity lives in the keychain and survives a reinstall — `preferredClientCertificateNames` carries `"trial-device"` precisely so it can be found again — but the trial marker, pinned CA, pinned host and device bearer token lived in `UserDefaults`, which iOS deletes with the container. `adoptExistingTrial` gates on those, so it reported the credential unrecoverable while it sat in the keychain. The device token genuinely was lost: derived from a pairing secret that exists only during pairing, and the rendezvous is put-once | `cde83c0` — one keychain item (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`), with one-time promotion of any `UserDefaults` copy. Sign-out purge is now load-bearing: uninstalling no longer takes the material with it |
| Every prompt failed: `spawn /usr/bin/codex ENOENT` | The base image unpacks node under `/opt/node`, so `npm install -g` lands the CLIs at `/opt/node/bin`, while `config.mjs` hardcoded `/usr/bin`. **Both harnesses unrunnable on every trial sandbox ever provisioned.** Cursor was unaffected only because its default derives from `CODEX_RUN_HOME` instead of guessing | `f8bc086` — resolve through `PATH` when the conventional path is absent; explicit env var still wins even pointing at nothing. `171bc4b` — the image names the paths and logs them at boot |
| Claude failed on every prompt | `--dangerously-skip-permissions cannot be used with root/sudo privileges`. The container is deliberately root (the base entrypoint starts envd, which mounts) and `CODEX_DANGEROUS_MODE` defaults on. Tested in the image (Claude Code 2.1.227): `--permission-mode bypassPermissions` is refused by the **same** guard, so dropping the flag is not a workaround | `bb533b0` — `IS_SANDBOX=1` in the trial image only. The claim is true here (a per-user microVM, destroyed at expiry) and it must never be a relayd default, where the guard protects a real machine |
| No model choice; Codex had no effort choice | The default catalog advertised one row per harness and nothing else, and Codex carried no `effortLevels` | `bb533b0` — each provider keeps a no-`taskModel` entry (the fallback that cannot break on an unentitled model) plus named models; every entry carries effort levels |
| `build.sh` reported three successful builds as failures | The readiness poll aborted on its own first pass: right after `POST /templates` returns 202 the detail response has no top-level `status`, `grep` exited 1, `pipefail` promoted it, `set -e` killed the script — printing neither the FAILED nor the timeout message | `0690c80` — unreadable status retries; only an explicit top-level `FAILED`/`ERROR` is fatal; both fatal paths print the last response. `test-status-parse.sh` runs the extraction under the same shell options, without which the bug is invisible |
| iOS build rejected by Apple | `hasMachine` short-circuited to `true` under `#if targetEnvironment(simulator)`, and `xcodebuild test` is a simulator build — so the assertion that a dead trial routes to the trial flow could never pass. Worse than a red build: a real regression would have stayed green | `f067a12` — the preview fixture is gated on a marker the launcher exports, not on "am I a simulator" |
| Unconfigured builds talked to the wrong host | `POC_VAULT_CODEX_BASE_URL` was checked in as `https://codex.pocs.conformal.live` in both configurations, and the device fallback matched. That host is live — it is the owner's own `pariksj-dev` box (`i-0364bb0f31f506e7c`), not the product | `e88e253` — build settings emptied, fallback is `https://unconfigured.invalid` (RFC 2606, can never resolve) so an unconfigured build fails at DNS instead of silently reaching somewhere |
